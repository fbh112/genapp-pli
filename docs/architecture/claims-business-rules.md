| Label | Meaning |

## 2. Claim identity and numbering

### R1 — Claim numbers are generated by Db2, starting at 1000001
**Business meaning:** every claim has a unique 7-digit number, issued in sequence.
**Type:** Explicit in the DDL. **Suspect** in the program.

- DDL: `ClaimNumber INTEGER NOT NULL GENERATED BY DEFAULT AS IDENTITY (START WITH 1000001, INCREMENT BY 1, CACHE 20)`, primary key ([`db2cre.jcl:354-355,362`](../../DDL/db2cre.jcl)). A unique clustered index `iClaim` is created on it ([`db2cre.jcl:369-371`](../../DDL/db2cre.jcl)).
- The program inserts a **host variable** for `ClaimNumber`: `:DB2_C_Num_INT` ([`LGAPDB01:556`](../../PLI%20Programs/LGAPDB01.pli)).
- `DB2_C_Num_INT` is declared `INIT(0)` ([`LGAPDB01:101`](../../PLI%20Programs/LGAPDB01.pli)), zeroed again at line 127, and **never assigned** from the request.
- `GENERATED BY DEFAULT` accepts an explicit value. So, as written, the insert supplies `0` instead of letting Db2 generate a number.
- After the insert, `CA_C_Num = DB2_C_Num_INT` ([`LGAPDB01:565`](../../PLI%20Programs/LGAPDB01.pli)), which returns the same value (0) to the caller.
- By contrast, policy numbers are fetched with `IDENTITY_VAL_LOCAL` in `INSERT_POLICY`. Claims have no equivalent.

**What the team needs to know:** the documented intent (generated numbers) and the coded behaviour (insert of 0) disagree. Which of the two the production system actually shows depends on the live data and on the caller. This cannot be settled from the workspace.

**Programs / data:** `LGAPDB01`, table `CLAIM`, field `CA_C_Num` (`PIC '9999999999'`, 10 digits).

### R2 — A claim belongs to exactly one policy
**Business meaning:** a claim is always made against one policy.
**Type:** Explicit.

- `PolicyNumber INTEGER NOT NULL` ([`db2cre.jcl:356`](../../DDL/db2cre.jcl)).
- The policy number comes from the request header: `DB2_C_PolicyNum_INT = CA_POLICY_NUM` ([`LGAPDB01:146`](../../PLI%20Programs/LGAPDB01.pli)).
- There is no limit on the number of claims per policy (inferred: no unique constraint besides `ClaimNumber`).

## 3. Policy linkage and referential integrity

### R3 — A claim can only be created for an existing policy
**Business meaning:** you cannot claim against a policy that does not exist.
**Type:** Explicit in the DDL. Inferred in the program, because no program checks it.

- Foreign key `(PolicyNumber) REFERENCES Policy (PolicyNumber) ON DELETE CASCADE` ([`db2cre.jcl:363-365`](../../DDL/db2cre.jcl)).
- `LGAPDB01` skips `INSERT_POLICY` for claims: `If (CA_REQUEST_ID <> '01ACLM') THEN CALL INSERT_POLICY` ([`LGAPDB01:195-197`](../../PLI%20Programs/LGAPDB01.pli)). So the claim reuses a policy created earlier.
- If the policy does not exist, Db2 rejects the insert. The program takes the generic error path (R14). The specific SQLCODE is not tested. It would probably be -530, but no code checks for it on the claim path (the `-530` branch exists only for policy inserts).

**What the team needs to know:** the existence check is performed by Db2, not by any program. Anything that replaces the Db2 constraint must reproduce it.

### R4 — Deleting a policy deletes its claims
**Business meaning:** claims have no life without their policy.
**Type:** Explicit in the DDL. The delete program says nothing about claims.

- `ON DELETE CASCADE` ([`db2cre.jcl:365`](../../DDL/db2cre.jcl)).
- `LGDPDB01` deletes only from `POLICY` ([`LGDPDB01:148-152`](../../PLI%20Programs/LGDPDB01.pli)). The comment mentions the cascade to "policy type" tables ([`LGDPDB01:141-143`](../../PLI%20Programs/LGDPDB01.pli)) but not claims.
- SQLCODE 100 (policy not found) is treated as success ([`LGDPDB01:154-160`](../../PLI%20Programs/LGDPDB01.pli)).
- The same cascade applies when a customer is deleted, if the customer FK cascades to `POLICY` (stated in the earlier impact analysis, not re-verified here).

**What the team needs to know:** there is no code anywhere that says "delete claims". The rule exists only in the DDL. The caller of a policy delete receives no indication that claims were also removed. Claims are deleted without an audit message.

### R5 — A claim has no customer of its own
**Type:** Inferred.

- The `CLAIM` table has no `CustomerNumber` column ([`db2cre.jcl:353-361`](../../DDL/db2cre.jcl)).
- The owner is found by joining through `POLICY`: `POLICY.CustomerNumber` ([`LGIPDB01:1080,1096-1098`](../../PLI%20Programs/LGIPDB01.pli)).
- Therefore moving a policy to a different customer (if that were possible) would change the claim's owner without touching `CLAIM`.

## 4. Claim creation (`01ACLM`)

### R6 — Request routing
**Type:** Explicit.

- `LGAPDB01` routes on `CA_REQUEST_ID` in two `SELECT` blocks: one sets `DB2_POLICYTYPE` ([`LGAPDB01:174`](../../PLI%20Programs/LGAPDB01.pli)), one calls the insert procedure ([`LGAPDB01:219-221`](../../PLI%20Programs/LGAPDB01.pli)).
- Any other value returns `'99'`. The first `SELECT` does `EXEC CICS RETURN` immediately ([`LGAPDB01:178-181`](../../PLI%20Programs/LGAPDB01.pli)). The second only sets the return code ([`LGAPDB01:223-225`](../../PLI%20Programs/LGAPDB01.pli)), after which the flow continues to `LGAPVS01`.
- The comparison is **case-sensitive** here. `LGDPOL01` and `LGIPDB01` uppercase the request ID first ([`LGDPOL01:97`](../../PLI%20Programs/LGDPOL01.pli), [`LGIPDB01:281`](../../PLI%20Programs/LGIPDB01.pli)); `LGAPDB01` does not (R20).

### R7 — Claim data is stored as supplied, with no validation
**Type:** Inferred (absence of code).

`INSERT_CLAIM` ([`LGAPDB01:538-575`](../../PLI%20Programs/LGAPDB01.pli)) does the following and nothing else:
1. Moves `CA_C_Paid` and `CA_C_Value` into 31-bit integers ([`:540-541`](../../PLI%20Programs/LGAPDB01.pli)).
2. Inserts policy number, date, the two amounts, `CA_C_CAuse` and `CA_C_Observations` ([`:544-563`](../../PLI%20Programs/LGAPDB01.pli)).

What is **not** checked anywhere in the programs read:
- that the claim date is a valid date, or falls within the policy period (issue and expiry dates exist on `POLICY` but are not read);
- that `Paid` ≤ `Value`;
- that `Paid` and `Value` are positive or non-zero;
- that `Cause` or `Observations` are present;
- that the policy is of a type that can be claimed against, or is still active;
- that the caller is the policy's owner (`CA_CUSTOMER_NUM` is copied to `DB2_CUSTOMERNUM_INT` and to the error message, but is not used in the claim insert).

**Only the database enforces anything:** `NOT NULL` on `PolicyNumber`, the date type of `ClaimDate`, and the foreign key. `Paid`, `Value`, `Cause` and `Observations` are nullable in the DDL.

### R8 — Length check covers the header only
**Type:** Inferred. **Suspect.**

- `LGAPDB01` starts at `WS_CA_HEADER_LEN` = 28 ([`LGAPDB01:56,151`](../../PLI%20Programs/LGAPDB01.pli)).
- Endowment, House and Motor add their `WS_FULL_x_LEN` ([`:156,161,166`](../../PLI%20Programs/LGAPDB01.pli)). **Commercial and Claim add nothing** — only the header size is required.
- A short COMMAREA gives `'98'` ([`:186-189`](../../PLI%20Programs/LGAPDB01.pli)).
- `LGAPOL01` does the same header-only check ([`LGAPOL01:103-110`](../../PLI%20Programs/LGAPOL01.pli)).
- A claim request that carries the header but not the claim body would therefore pass the length check, and the claim fields would be read from whatever follows. `WS_FULL_CLAIM_LEN` (618) exists in [`LGPOLICY.inc:24`](../../Includes/LGPOLICY.inc) and is used only on inquiry.

### R19 — `DB2_POLICYTYPE = 'X'`
**Type:** Inferred. A claim sets `DB2_POLICYTYPE` to `'X'` ([`LGAPDB01:174-176`](../../PLI%20Programs/LGAPDB01.pli)). That value is used by `INSERT_POLICY`, which claims skip. So the `'X'` code has no effect on claims. It may have been intended as a policy-type marker for a claim, but nothing records it.

### R15 — A claim add also writes the VSAM file `KSDSPOLY`
**Type:** Inferred. **Suspect.**

- `LGAPDB01` always links to `LGAPVS01` after the SELECT, regardless of request ID ([`LGAPDB01:229-231`](../../PLI%20Programs/LGAPDB01.pli)).
- `LGAPVS01` takes the 4th character of the request ID as the record type: `'C'` for `01ACLM` ([`LGAPVS01:84`](../../PLI%20Programs/LGAPVS01.pli)). `'C'` is also what `01ACOM` (Commercial) gives.
- With type `'C'` it fills the record using the **Commercial** fields `CA_B_Postcode`, `CA_B_Status` and `CA_B_Customer` ([`LGAPVS01:90-94`](../../PLI%20Programs/LGAPVS01.pli)).
- It then writes `KSDSPOLY`, length 64, key length 21 ([`LGAPVS01:126-131`](../../PLI%20Programs/LGAPVS01.pli)). Failure sets `'80'` and writes the error message ([`:133-138`](../../PLI%20Programs/LGAPVS01.pli)).
- In a claim request, those COMMAREA positions hold claim data (the `CA_CLAIM` layout overlays the policy-specific area, [`LGCMAREA.inc:102-109`](../../Includes/LGCMAREA.inc)), so the VSAM record contains bytes interpreted as postcode, status and customer.
- The record is keyed with the policy number and customer number copied from the header ([`LGAPVS01:85-86,124`](../../PLI%20Programs/LGAPVS01.pli)).

**What the team needs to know:** the system keeps a second copy of "something" per claim in `KSDSPOLY`. Whether any program reads it for claims is unknown (`LGIPVS01` is not in the workspace). Because the key is policy-based, it may collide with a record already written for the policy itself (not verified).

## 5. Claim retrieval

### R9 — Inquiry by claim number (`01ICLM`)
**Business meaning:** given a claim number, return the claim and its customer and policy.
**Type:** Explicit.

- Router: `DB2_CLAIMNUM_INT = CA_C_Num` then `GET_CLAIM_DB2_INFO_1` ([`LGIPDB01:314-317`](../../PLI%20Programs/LGIPDB01.pli)).
- Query: `POLICY` join `CLAIM` on `PolicyNumber`, filtered by `CLAIM.ClaimNumber` ([`LGIPDB01:1078-1100`](../../PLI%20Programs/LGIPDB01.pli)).
- Output fields: customer number, claim number, policy number, date, paid, value, cause, observations ([`:1080-1087`](../../PLI%20Programs/LGIPDB01.pli)).
- The join means **a claim whose policy does not exist cannot be retrieved** (it is inner-joined). In practice the foreign key (R3) prevents such rows.
- Outcome by SQLCODE ([`:1102-1148`](../../PLI%20Programs/LGIPDB01.pli)):

| SQLCODE | Behaviour |
|---|---|
| 0 | Check COMMAREA length first, then populate the response |
| 100 | `CA_RETURN_CODE = '01'` ("invalid customer / policy number" per the comment, though neither is used) |
| other | `'90'`, error message written |

- On success the required length is `WS_CA_HEADERTRAILER_LEN + WS_FULL_CLAIM_LEN` (618) ([`:1106-1107`](../../PLI%20Programs/LGIPDB01.pli)); a shorter area returns `'98'` ([`:1111-1114`](../../PLI%20Programs/LGIPDB01.pli)).
- The length check happens **after** the select, so a too-short area costs a Db2 read.

### R10 — Inquiry by customer (`02ICLM`)
**Business meaning:** list a customer's claims.
**Type:** Inferred. **Suspect.**

- Cursor `CusClaim_Cursor`, declared `Insensitive Scroll`, selects the same eight columns, with `POLICY.CustomerNumber = :DB2_CUSTOMERNUM_INT` ([`LGIPDB01:149-164`](../../PLI%20Programs/LGIPDB01.pli)).
- `GET_Claim_DB2_INFO_2` opens it (`'89'` on failure), loops `DO UNTIL (SQLCODE > 0)` calling the fetch procedure, then closes it (`'88'` on failure) ([`:1156-1178`](../../PLI%20Programs/LGIPDB01.pli)).
- Each fetch **overwrites the same COMMAREA fields** ([`:1197-1212`](../../PLI%20Programs/LGIPDB01.pli)). A customer with several claims gets only the last one in the response.
- Unlike the Commercial multi-row inquiries (`03ICOM`, `05ICOM`), the claim cursor does not write rows to the `ICOM` container ([`LGIPDB01:914-918`](../../PLI%20Programs/LGIPDB01.pli)).
- The fetch procedure has no error branch for a negative SQLCODE and no length check.
- **Loop condition:** `DO UNTIL (SQLCODE > 0)` terminates on SQLCODE 100 (or any other positive code). A *negative* SQLCODE does not terminate the loop, so a failing fetch would repeat with no explicit guard. This is a hazard the team should be aware of.
- If the open fails (`'89'`) the loop still runs.
- No rows: the loop ends on the first fetch (100) and the response fields keep their incoming values. The return code stays `'00'` — **an empty customer is not reported as `'01'`**, unlike `01ICLM`.
- Policy-common fields (`DB2_ISSUEDATE`, etc.) are copied into the COMMAREA ([`:1204-1209`](../../PLI%20Programs/LGIPDB01.pli)) though the claim `SELECT` does not populate them. They carry whatever the host variables held (initial values or earlier data in the same task).

### R11 — No ownership check on `01ICLM`
**Type:** Inferred. The select is filtered by claim number only ([`LGIPDB01:1097-1100`](../../PLI%20Programs/LGIPDB01.pli)). The customer and policy numbers in the request are ignored. The caller receives the claim's actual customer and policy numbers in the response, and nothing compares them with what was asked for. Any access control must live in the caller.

## 6. Supported operations

### R12 — Add and inquire only
**Type:** Explicit for delete. Inferred for update.

| Operation | Request ID | Behaviour | Where |
|---|---|---|---|
| Add | `01ACLM` | Supported | `LGAPDB01:219` |
| Inquire one | `01ICLM` | Supported | `LGIPDB01:314` |
| Inquire by customer | `02ICLM` | Supported (see R10) | `LGIPDB01:319` |
| Delete | `01DCLM` (not present) | `LGDPOL01` allows only `01DEND/01DHOU/01DCOM/01DMOT` and returns `'99'` otherwise ([`LGDPOL01:100-108`](../../PLI%20Programs/LGDPOL01.pli)). `LGDPDB01` does the same ([`LGDPDB01:123-131`](../../PLI%20Programs/LGDPDB01.pli)) | — |
| Update | `01UCLM` (not present) | `LGUPOL01` sets `'99'` for an unknown ID but **then calls `LGUPDB01` anyway** ([`LGUPOL01:128-132`](../../PLI%20Programs/LGUPOL01.pli)) | — |

- **Claims can only be created and read. There is no way to correct, close, pay or withdraw a claim** through the programs in the workspace. The `Paid` column is therefore written once, at creation.
- The only removal path is the cascade (R4).
- The `LGUPOL01` fall-through for an unknown ID is **Suspect**. What `LGUPDB01` does with a claim request was not traced (the scanner database did not capture its SQL).
- The business-rules hook in `LGAPOL01` (`BUSINESS_RULES = 'Y'`, calls `LGAPBR01`) applies only to `01AEND`, and is off by default ([`LGAPOL01:115-128`](../../PLI%20Programs/LGAPOL01.pli)). It does **not** apply to claims. `LGAPBR01` is not in the workspace.

## 7. Data content and format

### R17 — Formats and limits
**Type:** Explicit.

| Field | COMMAREA (`CA_CLAIM`) | Db2 column | Notes |
|---|---|---|---|
| Claim number | `PIC '9999999999'` (10 digits) | `INTEGER` | [`LGCMAREA.inc:103`](../../Includes/LGCMAREA.inc) |
| Date | `CHAR(10)` | `DATE` | No format is enforced in code. Db2 rejects a value that is not a valid date in a recognised format |
| Paid | `PIC '99999999'` (8 digits, unsigned) | `INTEGER` | Whole units only, no decimals, no sign |
| Value | `PIC '99999999'` | `INTEGER` | As above |
| Cause | `CHAR(255)` | `CHAR(255)` | Fixed length, blank padded |
| Observations | `CHAR(255)` | `CHAR(255)` | Fixed length, blank padded |

- Amounts are **whole numbers** with at most 8 digits. No currency field exists.
- The BMS claim screen `SSMAPP5` limits cause and observations to **25 characters** on input, although the data layout holds 255 ([`SSMAP.bms`](../../Maps/SSMAP.bms), from line 616). So claims entered from that screen are short, but the stored width is longer.
- `ClaimDate` is a `DATE`, so Db2 applies its date-format rules on insert. The program does not convert.
- Response length for a claim: `WS_CLAIM_LEN` = 546, `WS_FULL_CLAIM_LEN` = 618 ([`LGPOLICY.inc:19,24`](../../Includes/LGPOLICY.inc)).

### R18 — The `'FINAL'` end-of-data marker
**Type:** Explicit. On a successful inquiry, `'FINAL'` is written into the first five bytes of `CA_C_FILLER` ([`LGIPDB01:1134,1212`](../../PLI%20Programs/LGIPDB01.pli)). The comment says it "marks the end of the policy data". Callers may rely on it. In `02ICLM` it is written once per fetched row, so it appears in the response only if at least one row was returned.

### Inferred: how the response is assembled
- The claim fields are moved to the response **as a block**: `SUBSTR(CA_POLICY_RAW,1,WS_COMM_LEN) = DB2_CLAIM_TEXT` ([`LGIPDB01:1130,1211`](../../PLI%20Programs/LGIPDB01.pli)). `DB2_CLAIM_TEXT` (556 bytes) overlays `DB2_CLAIM_DATA` in a union ([`LGPOLICY.inc:106-114`](../../Includes/LGPOLICY.inc)), and `WS_COMM_LEN` is 1102.
- This means the response layout depends on the byte layout of `DB2_CLAIM` matching `CA_CLAIM`. Any change to either layout silently changes the response.

## 8. Error and return-code contract

### R13 — Return codes seen on claim paths
**Type:** Explicit.

| Code | Meaning | Set by (claim path) |
|---|---|---|
| `00` | Success | `LGAPDB01:141`, `LGIPOL01:84` |
| `01` | Claim not found (`01ICLM` only) | `LGIPDB01:1140` |
| `80` | VSAM write failed | `LGAPVS01:135` |
| `88` | Cursor close failed (`02ICLM`) | `LGIPDB01:1176` |
| `89` | Cursor open failed (`02ICLM`) | `LGIPDB01:1164` |
| `90` | Db2 error | `LGAPDB01:568`, `LGIPDB01:1144` |
| `98` | COMMAREA too short | `LGAPDB01:187`, `LGIPDB01:1112` |
| `99` | Unknown request ID | `LGAPDB01:179,224`, `LGIPDB01:324` |

- Codes are two-character strings in `CA_RETURN_CODE`.
- `02` (timestamp mismatch) and `70` (SQLCODE -530) are not used on claim paths. Note `70` is the **policy** foreign-key error; a claim insert with an unknown policy gets `90`, not `70`.
- `LGAPOL01` tests `CA_RETURN_CODE > 0` after the link ([`LGAPOL01:137`](../../PLI%20Programs/LGAPOL01.pli)), but returns in both branches, so the return code is simply passed back.

### R14 — A claim insert failure abends the task
**Business meaning:** a failed claim creation does not return a handled error. The task is terminated, and the unit of work is backed out.
**Type:** Explicit.

- On any non-zero SQLCODE: set `'90'`, write the error message, `EXEC CICS ABEND ABCODE('LGSQ') NODUMP` ([`LGAPDB01:567-573`](../../PLI%20Programs/LGAPDB01.pli)).
- The comment says the abend is "to cause backout of update to Policy table" ([`:570`](../../PLI%20Programs/LGAPDB01.pli)). This text was copied from the policy sub-table inserts. **For claims there is no policy insert to back out**; the abend simply undoes the failed claim.
- The `EXEC CICS RETURN` that follows is unreachable.
- Because the abend rolls back the whole task, the caller receives an abend rather than `'90'` on a claim insert failure. The `'90'` is visible only in the error queue.
- `NODUMP` is specified: no dump is taken.
- Missing COMMAREA also abends with `LGCA` on add and inquire ([`LGAPDB01:134-138`](../../PLI%20Programs/LGAPDB01.pli), [`LGIPOL01:77-80`](../../PLI%20Programs/LGIPOL01.pli)).
- Inquiry errors do **not** abend; they return a code.

### R16 — Error logging
**Type:** Explicit.

- Each program's `WRITE_ERROR_MESSAGE` links to the external `LGSTSQ` program, once with a header message and once with up to 90 bytes of the COMMAREA ([`LGAPOL01:165-179`](../../PLI%20Programs/LGAPOL01.pli), [`LGIPOL01:119-132`](../../PLI%20Programs/LGIPOL01.pli) show the pattern).
- The header message holds date, time, customer number, policy number, SQL request text and SQLCODE. For claims the SQL request text is `' INSERT CLAIM'` or `' SELECT Claim '`.
- The `LGAPDB01` message includes the hard-coded program label `' LGIPOL01'` ([`LGAPDB01:35`](../../PLI%20Programs/LGAPDB01.pli)). That is probably copy-paste — **Suspect**: anyone reading the error queue will see the wrong program name for claim insert failures.
- `LGSTSQ` is not in the workspace, so where messages end up (TS queue, TD queue) is not confirmed. Comments mention both the "CSMT" TD queue and a TS queue.
- Writing the message happens **before** the abend, so the log entry is made, then the work is undone. Whether the queue write survives the backout depends on the queue type (recoverable or not). Not verifiable here.

## 9. Transaction and concurrency behaviour

| Behaviour | Type | Evidence |
|---|---|---|
| The claim insert and the VSAM write run in the same CICS task, linked from `LGAPDB01`, and share one unit of work | Inferred | `LGAPDB01:229-234` has no `SYNCPOINT`. Db2 and VSAM are in the same task |
| An `LGSQ` abend backs out both | Inferred | CICS behaviour for the task. The comment at `LGAPDB01:570` states the intent |
| A VSAM failure (`'80'`) does **not** abend and does not roll back the Db2 insert | Inferred | `LGAPVS01:133-138` returns with `'80'`. `LGAPDB01` has no check after the link (line 229-234). The claim row remains while the caller sees `'80'` |
| No optimistic locking on claims | Inferred | `POLICY` has a `LASTCHANGED` timestamp used for update checks (return code `02`). `CLAIM` has no such column |
| No explicit locking or isolation choice for claim reads | Inferred | No `WITH UR/CS` clause appears in the claim SQL. The cursor is declared `Insensitive Scroll`, so it reads from a snapshot of the result |
| Claim number allocation is not serialised by the program | Inferred | Relies on the identity column (R1) |

**What the team needs to know:** the interaction between the Db2 insert, the VSAM write and the abend is the main transactional behaviour. A VSAM failure after a successful Db2 insert leaves a claim row with a failure return code.

## 10. Cross-cutting facts about shared code

- Claims share `LGAPDB01` and `LGIPDB01` with Endowment, House, Motor and Commercial. The claim branches are about 12 of 218 statements in `LGAPDB01` and 70 of 515 in `LGIPDB01`.
- 11 of 12 programs include `LGCMAREA`, so the claim layout shares storage with all policy-specific layouts. The claim fields start at the same offset as `CA_ENDOWMENT`, `CA_HOUSE`, `CA_MOTOR` and `CA_COMMERCIAL`.
- `LGAPOL01` / `LGIPOL01` contain no claim-specific logic. They apply the same header-length check, the same `LGCA` abend and the same error logging as for policies.
- The `CLAIM` table is granted `ALL` to `PUBLIC` ([`db2cre.jcl:400`](../../DDL/db2cre.jcl)). Any user with the plan can read or change it.
- The claim table has its own tablespace `GENATS07`, shared by no other table ([`db2cre.jcl:367`](../../DDL/db2cre.jcl)).

## 12. What this catalogue does not cover

- **Callers.** No program in the workspace sends `01ACLM`, `01ICLM` or `02ICLM`. Rules enforced in callers (screen validation, authorisation, claim-number entry, status handling) are not visible.
- **`LGUPDB01`.** Its SQL is not captured by the scanner database. A claim update path (A8) is unconfirmed.
- **`LGIPVS01`, `LGSTSQ`, `LGAPBR01`, `LGSETUP` and customer programs.** Missing from the workspace.
- **Live data.** Whether `ClaimNumber` is really 0 or generated, and whether duplicates exist, can only be known from the database.
- **Runtime configuration.** CSD attributes such as recoverability of queues and files, and Db2 plan options, were read only as far as the CSD files in `Resources/` define them.
- **Business policy not in code.** Eligibility, waiting periods, payment authorisation and fraud checks are not present in any file read.
