Application Boundaries & Component Hierarchy

The General Insurance Application (GenApp) is a multi-tier mainframe enterprise application engineered in PL/I and hosted on IBM z/OS CICS Transaction Server. It provides policy lifecycle management across multiple insurance domains—including Endowment, House, Motor, and Commercial policies—backed by IBM Db2 relational tables and synchronized VSAM Key-Sequenced Data Sets (KSDS). This document details the application boundaries, structural layering, component interactions, and data delegation architecture.

1. Overview

GenApp implements a decoupled, service-oriented architecture within CICS. The architecture separates user interaction, business rules evaluation, orchestration, data access, and diagnostics into dedicated components communicating through canonical CICS Communication Areas (COMMAREAs).

1.1 Key Architectural Highlights

  • Interface Decoupling: External consumers (3270 BMS terminals, CICS Web Services, REST/JSON gateways, and batch jobs) interact through uniform COMMAREA structures.
  • Tiered Separation of Concerns: Direct UI handling is isolated to presentation drivers, while business logic modules coordinate workflow execution and delegate database persistence to specialized Data Access Layer (DAL) programs.
  • Dual Persistence Strategy: The system maintains relational integrity within IBM Db2 while propagating synchronized secondary copies to high-speed VSAM KSDS files for optimized key-based lookups.
  • Centralized Diagnostics: Standardized logging routines capture execution context (EIBTRNID, EIBTRMID, EIBTASKN), format diagnostic payloads, and record audit trails into CICS Transient Data Queues (TDQ) and Temporary Storage Queues (TSQ).

The system boundaries span four primary runtime zones: External Ingestion & Presentation, Business Orchestration, Data Access Layer (DAL), and the Persistence Boundary.

3. Front-End and Ingestion Layer Decomposition

The presentation tier encapsulates user interaction and formats input requests into standardized business structures before forwarding them into downstream orchestrators.

3.1 3270 Terminal Driver (LGTESTP1)

  • Map Interaction: Handles terminal input/output mapped by the SSMAPP1 Basic Mapping Support (BMS) mapset (defined via SSMAP.inc).
  • Function Key Mapping:
    • F3: Exit application.
    • F5: Invoke Policy Inquiry (LGIPOL01).
    • F6: Invoke Policy Creation (LGAPOL01).
    • F7: Invoke Policy Deletion (LGDPOL01).
    • F8: Invoke Policy Update (LGUPOL01).
  • Payload Marshalling: Maps screen buffer attributes (Customer Number, Policy ID, Policy Type) into the canonical LGCMAREA layout prior to initiating EXEC CICS LINK.

3.2 Service Ingestion Gateways

  • Web Services & REST APIs: Web-based service requests arrive directly via CICS channels or COMMAREA interfaces mapped to identical structures, bypassing BMS screen formatting.
  • Batch Interfaces: Batch extract and update utilities invoke business orchestrators using standard programmatic CICS LINK conventions.

4. Business Logic and Service Orchestration Layer

The business tier encapsulates workflow coordination, pre-insert and post-retrieval validation, policy-specific domain calculations, and delegation to data access services.

4.1 Orchestrator Module Responsibilities

  • LGIPOL01 (Policy Inquiry Service): Validates input COMMAREA parameters, manages request tracing, delegates retrieval to LGIPDB01, and applies domain overrides.
  • LGAPOL01 (Policy Add Service): Validates incoming policy structures, coordinates with business rule calculation routines (LGAPBR01), and calls LGAPDB01.
  • LGDPOL01 (Policy Delete Service): Validates deletion keys and delegates cascading deletes to LGDPDB01.
  • LGUPOL01 (Policy Update Service): Coordinates field-level validation and delegates relational and VSAM updates to LGUPDB01.
  • LGAPBR01 (Endowment Rule Engine): Evaluates policy terms, payout limitations, and interest calculations against structured parameters defined in LGCMARER.inc.
