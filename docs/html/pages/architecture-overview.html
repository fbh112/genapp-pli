Application Architecture

1 Overview

GenApp is a CICS-based general insurance policy management application written in PL/I running on z/OS. It provides full lifecycle management for four distinct insurance policy types — Endowment, House, Motor, and Commercial — along with associated claim records.

The application is structured as a strict three-tier architecture, separating presentation, business logic, and data access concerns into distinct layers of CICS programs. All programs communicate exclusively through a shared 32,500-byte communication area (COMM_AREA) passed on every EXEC CICS LINK call, providing a consistent, typed interface across all tiers.

Key characteristics of the application:

  • CICS Transaction: SSP1 (entry point)
  • CICS Resource Group: GENASAP
  • Language: PL/I (z/OS)
  • Primary data store: DB2 (relational)
  • Secondary data store: VSAM KSDS (KSDSPOLY) — a parallel copy maintained in synchronisation with DB2
  • Inter-program communication: EXEC CICS LINK (static) and EXEC CICS LINK with runtime name resolution (dynamic)
  • Error logging: All programs delegate to the shared utility LGSTSQ via CICS LINK to write diagnostic messages to a CICS transient data queue

3 Layered Architecture Detail

3.1 Presentation Tier

The presentation tier consists of a single BMS mapset and a single terminal program.

  • SSMAP (BMS Mapset) — Defined in Maps/SSMAP.bms and included symbolically via Includes/SSMAP.inc. Contains map definitions SSMAPP1 through SSMAPP5 and SSMAPC1, though only SSMAPP1 is actively used by LGTESTP1.
  • LGTESTP1 — The sole entry-point CICS program. It sends and receives BMS map SSMAPP1, interprets PF key and ENTER inputs, populates the COMM_AREA, and dispatches to one of the four business logic programs via EXEC CICS LINK.
CODE 
/* Example: LGTESTP1 dispatching to LGAPOL01 via CICS LINK */
EXEC CICS LINK
    PROGRAM('LGAPOL01')
    COMMAREA(COMM_AREA)
    LENGTH(COMM_AREA_LEN);

LGTESTP1 also handles HANDLE AID for PF key routing, HANDLE CONDITION for CICS condition management, and issues SYNCPOINT ROLLBACK in error scenarios to ensure transactional integrity.

3.2 Business Logic Tier

The business logic tier contains four programs, one per CRUD operation. Their naming convention follows LGxPOL01 where x encodes the operation:

Program Operation Cyclomatic Score
LGAPOL01 Add Policy 9
LGIPOL01 Inquire Policy 6
LGDPOL01 Delete Policy 8
LGUPOL01 Update Policy 11

Each program in this tier is intentionally lightweight. Responsibilities are limited to:

  1. Receiving and validating the incoming COMM_AREA
  2. Determining the appropriate data-tier program(s) to call
  3. Issuing EXEC CICS LINK (or dynamic LINK) to the DB2 and/or VSAM access programs
  4. Propagating response codes back to the presentation tier
  5. Logging errors to the LGSTSQ utility

No SQL is executed directly in this tier. All data access is strictly delegated downward.

CODE 
/* Example: LGAPOL01 conditionally calling the ODM rules engine */
IF BUSINESS_RULES = 'Y' THEN
    EXEC CICS LINK
        PROGRAM('LGAPBR01')
        COMMAREA(COMM_AREA)
        LENGTH(COMM_AREA_LEN);

3.3 DB2 Data Access Tier

The DB2 access tier contains four programs (LGxPDB01) that encapsulate all SQL execution. No other tier contains EXEC SQL statements, ensuring a clean separation of data access concerns.

Program Operation Cyclomatic Score Key SQL Operations
LGAPDB01 Add Policy 26 INSERT into POLICY, type table, CLAIM; SELECT to retrieve assigned policy number
LGIPDB01 Inquire Policy 70 SELECT, FETCH (cursors) across all tables; CICS Containers for large result sets
LGDPDB01 Delete Policy 8 DELETE from POLICY; cascades to VSAM via LGDPVS01
LGUPDB01 Update Policy — SELECT FOR UPDATE (cursor lock); UPDATE on type table and POLICY; calls LGUPVS01

LGIPDB01 is the most complex program in the entire application (cyclomatic score of 70, 15 internal procedures). It is also the only program that uses CICS Channels and Containers (GET CONTAINER / PUT CONTAINER) to handle the large result sets that a policy inquiry may return.

CODE 
/* Example: LGIPDB01 returning data via a CICS Container */
EXEC CICS PUT CONTAINER(CONTAINER_NAME)
    FROM(POLICY_DATA)
    FLENGTH(DATA_LENGTH)
    CHANNEL(CHANNEL_NAME);
CODE 
/* Example: LGUPDB01 using SELECT FOR UPDATE cursor to lock a policy row */
EXEC SQL DECLARE POLICY_CUR CURSOR FOR
    SELECT POLICYNUMBER, LASTCHANGED
    FROM POLICY
    WHERE POLICYNUMBER = :WS-POLICYNUM
    FOR UPDATE OF LASTCHANGED;

3.4 VSAM Data Access Tier

The VSAM access tier provides a parallel persistence path to the KSDSPOLY KSDS file. This tier mirrors the DB2 operations to keep the VSAM copy in synchronisation with the DB2 master.

Program Operation CICS File Command
LGAPVS01 Add Policy EXEC CICS WRITE FILE
LGDPVS01 Delete Policy EXEC CICS DELETE FILE
LGUPVS01 Update Policy EXEC CICS READ FILE (exclusive) + EXEC CICS REWRITE FILE

Note: There is no LGIPVS01. Inquire operations read exclusively from DB2; the VSAM file is write/delete/update only from an application perspective.

CODE 
/* Example: LGUPVS01 performing a locked read before rewrite */
EXEC CICS READ FILE('KSDSPOLY')
    INTO(VSAM_RECORD)
    RIDFLD(POLICY_KEY)
    UPDATE;

/* ... modify VSAM_RECORD fields ... */

EXEC CICS REWRITE FILE('KSDSPOLY')
    FROM(VSAM_RECORD)
    LENGTH(RECORD_LEN);

4 Inter-Program Communication

4.1 The COMM_AREA Contract

Every program in the application — from LGTESTP1 down to the VSAM access programs — communicates through a single shared structure: the COMM_AREA, defined in Includes/LGCMAREA.inc. It is 32,500 bytes in length and is implemented as a union with a pointer (COMM_AREA_PTR) to allow flexible access patterns.

This structure carries:

  • The operation request code
  • Customer and policy identifiers
  • Policy type discriminator
  • Type-specific policy detail fields
  • Response and error codes
CODE 
/* LGCMAREA.inc — Universal communication area */
DCL COMM_AREA_PTR POINTER;
DCL 1 COMM_AREA BASED(COMM_AREA_PTR),
      3 CA_REQUEST_ID    CHAR(6),
      3 CA_RETURN_CODE   FIXED BIN(31),
      3 CA_CUSTOMER_NUM  CHAR(10),
      3 CA_POLICY_NUM    CHAR(10),
      3 CA_POLICY_TYPE   CHAR(1),
      /* ... additional fields per policy type ... */
      3 CA_DATA          CHAR(32460);

4.2 Static vs Dynamic CICS LINK

Not all inter-program calls use the same linking mechanism. The table below summarises which calls are static (program name hardcoded at compile time) and which are dynamic (program name resolved at runtime):

Caller Callee Link Type Rationale
LGTESTP1 LGAPOL01, LGIPOL01, LGDPOL01, LGUPOL01 Static CICS LINK Fixed dispatch — operation determined by PF key
LGAPOL01 LGAPDB01, LGAPVS01 Static CICS LINK Always the same target programs
LGIPOL01 LGIPDB01 Dynamic CICS LINK Program name resolved at runtime
LGDPOL01 LGDPDB01 Dynamic CICS LINK Program name resolved at runtime
LGDPDB01 LGDPVS01 Static CICS LINK Cascaded delete — fixed target
LGUPOL01 LGUPDB01 Static CICS LINK Fixed dispatch
LGUPDB01 LGUPVS01 Static CICS LINK Synchronisation step — fixed target

Dynamic linking allows the Inquire and Delete business logic programs to defer resolution of the backing data program until runtime, which can support environment-specific overrides or future substitution without recompilation of the business logic tier.

CODE 
/* Example: LGIPOL01 using dynamic link — program name in a variable */
DCL DB2_PROGRAM CHAR(8) INIT('LGIPDB01');

EXEC CICS LINK
    PROGRAM(DB2_PROGRAM)
    COMMAREA(COMM_AREA)
    LENGTH(COMM_AREA_LEN);

4.3 Error Logging via LGSTSQ

Every program in all tiers shares a common error-reporting pattern: on any abnormal condition, the program issues a CICS LINK to LGSTSQ, a COBOL utility that writes a diagnostic message to a CICS transient data queue. This pattern is consistent across all 11 PL/I programs.

CODE 
/* Standard error logging pattern used across all programs */
EXEC CICS LINK
    PROGRAM('LGSTSQ')
    COMMAREA(ERROR_MSG)
    LENGTH(ERROR_MSG_LEN);

5 Data Flows by Operation

The following sections describe the end-to-end call chain and data operations for each of the four policy operations.

5.1 Add Policy Flow

sequenceDiagram participant T as LGTESTP1 participant A as LGAPOL01 participant BR as LGAPBR01 (optional) participant D as LGAPDB01 participant V as LGAPVS01 participant DB2 as DB2 Tables participant VSAM as KSDSPOLY T->>A: CICS LINK (COMM_AREA) A->>A: Validate COMM_AREA alt BUSINESS_RULES = 'Y' A->>BR: CICS LINK (ODM validation) BR-->>A: Validation result end A->>D: CICS LINK D->>DB2: INSERT into POLICY D->>DB2: INSERT into MOTOR / HOUSE / ENDOWMENT / COMMERCIAL D->>DB2: INSERT into CLAIM D->>DB2: SELECT policy number (read-back) DB2-->>D: Assigned policy number D-->>A: COMM_AREA (policy number populated) A->>V: CICS LINK (VSAM path) V->>VSAM: EXEC CICS WRITE FILE VSAM-->>V: Write confirmation V-->>A: Return A-->>T: COMM_AREA (response)

After LGTESTP1 dispatches to LGAPOL01, the business logic program optionally invokes the ODM rules engine (LGAPBR01) when the BUSINESS_RULES flag is set to 'Y' (disabled by default). It then always calls LGAPDB01 to perform the DB2 inserts, which span the POLICY master table, one policy-type detail table, and the CLAIM table. The newly assigned policy number is read back via a SELECT before control returns. In parallel, LGAPVS01 writes the same record to the KSDSPOLY VSAM file.

5.2 Inquire Policy Flow

sequenceDiagram participant T as LGTESTP1 participant I as LGIPOL01 participant D as LGIPDB01 participant DB2 as DB2 Tables T->>I: CICS LINK (COMM_AREA) I->>I: Validate COMM_AREA I->>D: CICS DYNAMIC_LINK D->>DB2: SELECT from POLICY D->>DB2: SELECT / FETCH from type table D->>DB2: SELECT / FETCH from CLAIM DB2-->>D: Result rows D->>D: PUT CONTAINER (channel data) D-->>I: COMM_AREA + channel I-->>T: COMM_AREA + channel

The Inquire operation uses a dynamic CICS LINK, meaning the name LGIPDB01 is resolved at runtime rather than being hardcoded at compile time. LGIPDB01 is the most complex program in the application, employing multiple DB2 cursors and CICS Channels/Containers to return potentially large result sets to the caller. There is no VSAM read path for Inquire — DB2 is the authoritative read source.

5.3 Delete Policy Flow

sequenceDiagram participant T as LGTESTP1 participant DL as LGDPOL01 participant DD as LGDPDB01 participant DV as LGDPVS01 participant DB2 as DB2 Tables participant VSAM as KSDSPOLY T->>DL: CICS LINK (COMM_AREA) DL->>DL: Validate COMM_AREA DL->>DD: CICS DYNAMIC_LINK DD->>DB2: DELETE from POLICY DB2-->>DD: Delete confirmation DD->>DV: CICS LINK (cascade) DV->>VSAM: EXEC CICS DELETE FILE VSAM-->>DV: Delete confirmation DV-->>DD: Return DD-->>DL: COMM_AREA (response) DL-->>T: COMM_AREA (response)

Delete uses a cascaded approach: LGDPDB01 deletes the POLICY master row from DB2 and then immediately triggers LGDPVS01 to remove the corresponding record from KSDSPOLY. The VSAM deletion is therefore always an atomic consequence of the DB2 deletion — both are always performed together within the same CICS task.

5.4 Update Policy Flow

sequenceDiagram participant T as LGTESTP1 participant U as LGUPOL01 participant UD as LGUPDB01 participant UV as LGUPVS01 participant DB2 as DB2 Tables participant VSAM as KSDSPOLY T->>U: CICS LINK (COMM_AREA) U->>U: Validate COMM_AREA U->>UD: CICS LINK UD->>DB2: SELECT FOR UPDATE (cursor lock on POLICY) DB2-->>UD: Locked row UD->>DB2: UPDATE MOTOR / HOUSE / ENDOWMENT UD->>DB2: UPDATE POLICY (timestamp refresh) UD->>DB2: SELECT LASTCHANGED (read-back) DB2-->>UD: New timestamp UD->>UV: CICS LINK (sync) UV->>VSAM: EXEC CICS READ FILE (exclusive lock) VSAM-->>UV: Locked record UV->>VSAM: EXEC CICS REWRITE FILE VSAM-->>UV: Rewrite confirmation UV-->>UD: Return UD-->>U: COMM_AREA (response) U-->>T: COMM_AREA (response)

The Update flow uses a SELECT FOR UPDATE cursor to establish a pessimistic lock on the POLICY row before any changes are made, preventing concurrent updates. After updating both the type-specific detail table and the POLICY master row, LGUPDB01 reads back the new LASTCHANGED timestamp and then delegates to LGUPVS01 to synchronise the VSAM record using an exclusive READ FILE followed by REWRITE FILE.

6 Dual Persistence Model

GenApp maintains two persistent copies of every policy record simultaneously: DB2 as the primary relational store and KSDSPOLY (a VSAM KSDS) as a parallel copy. The following diagram summarises the synchronisation strategy per operation:

graph TD ADD[Add Policy] -->|LGAPDB01| DB2W[DB2 INSERT] ADD -->|LGAPVS01| VSAMW[VSAM WRITE] INQ[Inquire Policy] -->|LGIPDB01| DB2R[DB2 SELECT] INQ -.->|No VSAM read| NOVS[VSAM not consulted] DEL[Delete Policy] -->|LGDPDB01| DB2D[DB2 DELETE] DB2D -->|cascade via LGDPVS01| VSAMD[VSAM DELETE] UPD[Update Policy] -->|LGUPDB01| DB2U[DB2 UPDATE] DB2U -->|sync via LGUPVS01| VSAMU[VSAM REWRITE]

The synchronisation rules are:

Operation DB2 Action VSAM Action Trigger for VSAM
Add INSERT (via LGAPDB01) WRITE (via LGAPVS01) Called independently by LGAPOL01
Inquire SELECT (via LGIPDB01) None — not read DB2 is authoritative read source
Delete DELETE (via LGDPDB01) DELETE (via LGDPVS01) Cascaded by LGDPDB01
Update UPDATE (via LGUPDB01) REWRITE (via LGUPVS01) Called by LGUPDB01 after DB2 update
