Impact Analysis: Motor Policy EEPOS Migration

This technical document provides a comprehensive impact analysis for migrating Motor Policy lifecycle operations and persistence from the mainframe z/OS DB2 and VSAM tiers to an external distributed platform called EEPOS, accessed via RESTful APIs. It evaluates the architectural changes, code modifications, database restructuring, hidden dependencies, risk factors, and migration phases across the GenApp application.

1. Overview

The primary objective of this modernization initiative is to decouple high-volume motor insurance workflows from legacy mainframe processing. By offloading DB2 and VSAM storage and MIPS consumption for motor lines of business, the organization enables agile microservice development in EEPOS while maintaining 3270 terminal compatibility during and after the transition.

1.1 Change Specification

  • Title: Migration of Motor Policy Management and Relational Data to Distributed System (EEPOS) via REST API
  • Type: Migration / Modernization / Decomposition
  • Application Context: GenApp General Insurance Application (CICS / PL/I / DB2 / VSAM / BMS)
  • Entry Points:
    • Terminal 3270 BMS Map: Transaction SSP1 driving LGTESTP1.pli
    • Business Layer Programs: LGIPOL01.pli, LGAPOL01.pli, LGUPOL01.pli, LGDPOL01.pli
    • Data Layer Programs: LGIPDB01.pli, LGAPDB01.pli, LGUPDB01.pli, LGDPDB01.pli, LGAPVS01.pli, LGUPVS01.pli, LGDPVS01.pli

1.2 Scope Definition

In-Scope Items

  1. BMS Menu & UI Layer: Refactoring LGTESTP1.pli to invoke EEPOS REST APIs using EXEC CICS WEB or outbound HTTP facilities rather than linking internally to LGxPOL01 modules.
  2. Business & Persistence Layers:
    • Deprecating or modifying request routing (01IMOT, 01AMOT, 01UMOT, 01DMOT) in business modules (LGAPOL01, LGIPOL01, LGUPOL01, LGDPOL01).
    • Decommissioning DB2 motor SQL routines (INSERT_MOTOR, GET_MOTOR_DB2_INFO, UPDATE_MOTOR_DB2_INFO) in data modules (LGAPDB01, LGIPDB01, LGUPDB01, LGDPDB01).
    • Deprecating motor branch processing ('M') in VSAM mirror programs (LGAPVS01, LGUPVS01, LGDPVS01).
  3. Database & Data Tier:
    • Dropping DB2 table <DB2DBID>.MOTOR and index <DB2DBID>.iMotor.
    • Migrating existing motor policy data from DB2 MOTOR, DB2 POLICY (where POLICYTYPE = 'M'), and VSAM KSDSPOLY records into EEPOS.
  4. Copybooks / Shared Includes: Auditing LGCMAREA.inc (CA_MOTOR overlay) and LGPOLICY.inc (DB2_MOTOR definitions and lengths).

Out-of-Scope Items

  • Non-motor policy types: Endowment (01xEND), House (01xHOU), Commercial (01xCOM), and Claims (01xCLM).
  • Customer Master management (LGACDB01 and DB2 table <DB2DBID>.CUSTOMER).
  • Common infrastructure utilities such as the Temporary Storage Queue logger (LGSTSQ).

2. System Architecture & Context

2.1 Current vs. Target Architecture

In the legacy architecture, 3270 terminal users run transaction SSP1, invoking LGTESTP1.pli. This program issues EXEC CICS LINK calls to the policy business logic tier (LGxPOL01), which in turn calls both DB2 data programs (LGxPDB01) and VSAM mirror programs (LGxPVS01) in a dual-persistence pattern.

In the target architecture, LGTESTP1.pli acts as a direct REST client using CICS Web services to interact with the EEPOS platform over HTTPS. Motor data persistence and business logic are entirely externalized to the EEPOS distributed cloud platform.

2.2 Target Operational Sequence

When an inquiry, insert, update, or delete request is submitted via the SSP1 3270 screen, the updated LGTESTP1 program translates the BMS map fields to a JSON payload, communicates with EEPOS using standard CICS HTTP primitives, and maps the REST response back to the terminal map.

4. Deep Architectural Findings & Hidden Dependencies

Analysis of the PL/I source and database definitions revealed several critical dependencies that must be accounted for during the migration:

4.1 Hardcoded Motor Business Logic in Generic Programs

In LGIPOL01.pli, hardcoded motor business rules modify policy attributes dynamically. When motor processing is extracted to EEPOS, these business rules must be ported to the EEPOS service:

PLI 
IF CA_M_MAKE = 'HONDA' THEN
   CA_EXPIRY_DATE = '2099-01-01';

4.2 DB2 Foreign Key Cascade Deletes

In DDL/db2cre.jcl, the MOTOR table is defined with a cascading foreign key:

SQL 
FOREIGN KEY(policyNumber) REFERENCES <DB2DBID>.policy (policyNumber) ON DELETE CASCADE

Because LGDPDB01.pli deleted policies directly from POLICY and relied on DB2’s cascade delete to purge MOTOR:

SQL 
DELETE FROM POLICY WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT AND POLICYNUMBER = :DB2_POLICYNUM_INT;

Once the database structures are decoupled, mainframe policy deletions will no longer cascade to motor tables in EEPOS. Deletions must be handled explicitly through EEPOS APIs.

4.3 Dual-Persistence Mirroring (DB2 + VSAM)

The legacy architecture updates DB2 via LGxPDB01 and immediately calls LGxPVS01 to mirror writes to the VSAM dataset KSDSPOLY. Migration to EEPOS requires decommissioning both the DB2 tables and the VSAM record routines to avoid data drift.

4.4 COMMAREA Union Overlays and Length Calculations

The shared communication structure (LGCMAREA) uses a 32,500-byte buffer with union overlays for policy types. Programs such as LGAPOL01.pli calculate buffer lengths dynamically:

PLI 
WS_REQUIRED_CA_LEN = WS_CA_HEADER_LEN + WS_FULL_MOTOR_LEN;

Modifying offsets or removing members within LGPOLICY.inc without recompiling dependent modules could cause return code 98 (Commarea length too short) across non-motor policy types (Endowment, House, Commercial).

4.5 Distributed Transactions and CICS Syncpoints

LGTESTP1.pli uses local CICS syncpoints:

PLI 
EXEC CICS Syncpoint Rollback;

Calling external REST services means a local CICS rollback will not roll back changes in EEPOS. An idempotent API design and compensating transaction pattern must be implemented in EEPOS.

5. Change Propagation and Data Flow

The decommissioning of motor operations impacts the entire processing chain from API definition to UI refactoring and database teardown:

graph TD MIG[Decision: Move Motor Policy to EEPOS] --> API[Define EEPOS REST API Contracts] MIG --> DATA[Data Migration: DB2 & VSAM to EEPOS] API --> CICS_WEB[Implement CICS Outbound REST in LGTESTP1] API --> EEPOS_SRV[Build EEPOS Microservices & DB] CICS_WEB --> MOD_UI[Update LGTESTP1.pli to call EEPOS] MOD_UI --> DECOM_OL[Deprecate Motor Request IDs in LGxPOL01] DECOM_OL --> DECOM_DB[Remove Motor SQL Routines in LGxPDB01] DECOM_OL --> DECOM_VS[Remove Motor Logic in LGxPVS01] DATA --> DROP_DB2[Drop DB2 MOTOR Table & Index iMotor] DATA --> CLEAN_VSAM[Purge 'M' Records from KSDSPOLY] DECOM_DB --> CLEAN_INC[Audit LGPOLICY.inc & LGCMAREA.inc] CLEAN_INC --> RECOMPILE[Recompile Policy Suite & Test]

Accompanying the diagram above, the technical migration path follows these dependencies:

  1. Contract Definition: Establishing OpenAPI specs unblocks both EEPOS microservice creation and CICS client enablement in LGTESTP1.pli.
  2. Mainframe Decoupling: Once the UI routes to EEPOS directly, the internal business (LGxPOL01), DB2 (LGxPDB01), and VSAM (LGxPVS01) paths are deprecated.
  3. Storage Teardown: After delta data migration, the DB2 MOTOR table and VSAM 'M' keys are purged, followed by copybook cleanups and full test recompilation.

6. Risk Assessment and Mitigation Strategies

Risk Likelihood Impact Category Mitigation Strategy
Network Latency & Timeout in 3270 Session High High Performance / UX Configure non-blocking HTTP timeouts on EXEC CICS WEB CONVERSE; implement graceful error handling with user-friendly messages on BMS map SSMAPP1.
Data Integrity / Incomplete Dual-Write Migration High High Data Integrity Execute bulk historical data migration during a maintenance window; employ data validation reconciliation scripts between DB2/VSAM and EEPOS.
Lack of Distributed Transaction Rollback Medium High Operational / Integrity Implement idempotent APIs in EEPOS; design compensating REST calls in LGTESTP1 if subsequent CICS operations fail.
CICS Outbound Security & Certificate Management Medium Medium Security / Auth Install EEPOS TLS/SSL CA certificates in the z/OS RACF / TopSecret keyring; configure CICS URIMAP with appropriate Basic/Bearer token credentials.
Regression in Other Policy Types (Endow, House, Comm) Low High Regression Isolate changes in LGCMAREA.inc / LGPOLICY.inc; run comprehensive regression test suites for Endowment, House, and Commercial transactions.

7.2 Five-Phase Transition & Execution Plan

  • Phase 1: Preparation & API Foundation (Weeks 1–3)
    • Finalize EEPOS REST API contracts for Inquire, Add, Update, and Delete Motor Policy operations.
    • Stand up EEPOS services in non-production environments with required schemas.
    • Configure z/OS Communications Server, CICS TCPIPSERVICE, URIMAP, and RACF TLS keyrings for outbound CICS HTTP calls.
  • Phase 2: Dual-Read & Prototype Client (Weeks 4–6)
    • Develop and prototype REST outbound client routines in LGTESTP1.pli.
    • Perform an initial data snapshot from DB2 MOTOR and POLICY tables to EEPOS.
    • Validate EEPOS API responses against LGIPDB01 outputs.
  • Phase 3: Mainframe Refactoring & Decoupling (Weeks 7–8)
    • Refactor LGTESTP1.pli to switch completely to EEPOS REST APIs for Option 1 (Inquire), Option 2 (Add), Option 3 (Delete), and Option 4 (Update).
    • Remove motor-specific procedures (INSERT_MOTOR, GET_MOTOR_DB2_INFO, UPDATE_MOTOR_DB2_INFO) in LGAPDB01, LGIPDB01, LGUPDB01, and LGDPDB01.
    • Update LGAPVS01, LGUPVS01, and LGDPVS01 to bypass VSAM writes for 'M' policy records.
  • Phase 4: Data Cutover & Full Integration Testing (Weeks 9–10)
    • Execute final delta data migration from DB2 MOTOR to EEPOS database.
    • Run full regression testing of 3270 screens (SSP1, SSMAPP1) and non-motor policy types (Endowment, House, Commercial).
    • Verify end-to-end exception scenarios including network timeouts, service errors, and invalid inputs.
  • Phase 5: Decommissioning & Cleanup (Week 11)
    • Drop DB2 Table <DB2DBID>.MOTOR and Index <DB2DBID>.iMotor via DDL.
    • Clean up unused constants and host structures in Includes/LGPOLICY.inc.
    • Archive legacy motor batch jobs and backup artifacts.
