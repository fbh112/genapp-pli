Program Inventory & Functional Summary

This document provides a comprehensive inventory of all PL/I programs in the GenApp insurance application, summarizing their roles, business functions, interdependencies, and processing logic. The application is built on a CICS/DB2 mainframe stack and supports insurance policy lifecycle operations — including policy inquiry, data retrieval, and business rule enforcement — across multiple policy types: Endowment, House, Motor, and Commercial.

1. Overview

The GenApp PL/I application is a CICS-hosted, DB2-backed insurance policy management system. It follows a layered architecture that separates business logic from data access concerns. Programs communicate via CICS COMMAREA passing, and shared diagnostic utilities ensure consistent error logging across the application.

The application currently contains the following PL/I programs:

Program Role Primary Function
LGIPOL01 Business Logic Front-End Policy inquiry coordination, business rule enforcement
LGIPDB01 Data Access Back-End DB2 policy record retrieval across all policy types
LGSTSQ Shared Utility Transient Data Queue (TDQ) error logging

Each program occupies a distinct layer: presentation/business logic → data access → utility services. This separation ensures that business rules are applied consistently at the front-end layer, while data concerns are isolated in the backend.

2. System Architecture

The overall system architecture reflects a classic three-tier CICS/DB2 mainframe pattern. An external caller (a CICS transaction or another program) invokes the business logic tier, which coordinates with the data access tier and utility services.

The architecture enforces a strict call direction: callers invoke LGIPOL01, which is the sole entry point into the business layer. LGIPOL01 then delegates downward to LGIPDB01 for data retrieval, and sideways to LGSTSQ for error logging. No program calls upward in the hierarchy.

3. Program Inventory

3.1 LGIPOL01 — Policy Inquiry Business Logic Front-End

3.1.1 Role and Purpose

LGIPOL01 is the primary entry point for insurance policy inquiry transactions. It acts as the business logic coordinator: validating inputs, delegating database retrieval, applying post-retrieval business rules, and returning a fully populated response to the caller. It supports all four policy types: Endowment, House, Motor, and Commercial.

3.1.2 Business Functions Performed

# Business Function Description
1 COMMAREA Validation Verifies that a valid input payload was received; abends with LGCA if missing
2 Policy Inquiry Coordination Passes customer and policy identifiers to LGIPDB01 for DB2 retrieval
3 Honda Expiry Date Override Overrides policy expiry to 2099-01-01 for all motor policies with vehicle make HONDA
4 Diagnostic Error Logging Writes timestamped error records and raw COMMAREA snapshots to the TDQ via LGSTSQ

3.1.3 Key Inputs and Outputs

Direction Field Description
Input CA_CUSTOMER_NUM 10-digit customer identifier
Input CA_POLICY_NUM 10-digit policy identifier
Input EIBCALEN CICS-provided COMMAREA length (must be > 0)
Output CA_RETURN_CODE '00' on success; overwritten by LGIPDB01 on error
Output CA_EXPIRY_DATE Policy expiry date; conditionally overridden to '2099-01-01'
Output CA_M_MAKE Vehicle make for motor policies
Output COMM_AREA Fully populated response returned to the caller

3.1.4 Business Rules

Rule 1 — Initialize Policy Inquiry Return Code

Before any processing, the return code is set to a default success state:

PL1 
CA_RETURN_CODE = '00';

Rule 2 — Delegate Policy Lookup to Backend

The full COMMAREA is forwarded to the DB2 access layer via a synchronous CICS LINK:

PL1 
EXEC CICS LINK Program(LGIPDB01)
           Commarea(COMM_AREA)
           Length(32000);

Rule 3 — Honda Vehicle Policy Expiry Date Override

After database retrieval, a special underwriting rule is applied: any motor policy insuring a Honda vehicle is granted an effectively indefinite coverage period:

PL1 
IF CA_M_MAKE = 'HONDA' THEN
   CA_EXPIRY_DATE = '2099-01-01';

⚠️ This comparison is case-sensitive and fixed-length padded (PL/I CHAR(15) semantics). Only the exact value 'HONDA' with trailing blanks will trigger the override.

3.2 LGIPDB01 — Policy Data Access Back-End

3.2.1 Role and Purpose

LGIPDB01 is the data access layer program responsible for executing DB2 SQL queries to retrieve full policy records. It is exclusively invoked by LGIPOL01 via EXEC CICS LINK and is never called directly by external transactions. It populates all policy-type-specific fields in the COMMAREA and sets CA_RETURN_CODE to reflect the outcome of the database operation.

3.2.2 Business Functions Performed

# Business Function Description
1 Customer Record Retrieval Queries the DB2_CUSTOMER table for personal details matching CA_CUSTOMER_NUM
2 Policy Record Retrieval Queries the DB2_POLICY table for the policy matching CA_POLICY_NUM
3 Policy-Type Detail Retrieval Queries the appropriate detail table (Endowment, House, Motor, Commercial) based on DB2_POLICYTYPE
4 Return Code Population Sets CA_RETURN_CODE in the COMMAREA to reflect DB2 query outcomes

3.2.3 Database Entities Accessed

erDiagram DB2_CUSTOMER { int CA_CUSTOMER_NUM PK string FIRST_NAME string LAST_NAME date DATE_OF_BIRTH string ADDRESS string PHONE_NUMBER string EMAIL_ADDRESS } DB2_POLICY { int DB2_POLICYNUMBER PK int CA_CUSTOMER_NUM FK string DB2_POLICYTYPE date CA_ISSUE_DATE date CA_EXPIRY_DATE decimal CA_PAYMENT } DB2_MOTOR { int DB2_POLICYNUMBER FK string CA_M_MAKE } DB2_ENDOWMENT { int DB2_POLICYNUMBER FK decimal CA_E_SUM_ASSURED } DB2_HOUSE { int DB2_POLICYNUMBER FK string PROPERTY_DETAILS } DB2_COMMERCIAL { int DB2_POLICYNUMBER FK string CA_B_PROPTYPE } DB2_CUSTOMER ||--o{ DB2_POLICY : owns DB2_POLICY ||--o| DB2_MOTOR : "type M" DB2_POLICY ||--o| DB2_ENDOWMENT : "type E" DB2_POLICY ||--o| DB2_HOUSE : "type H" DB2_POLICY ||--o| DB2_COMMERCIAL : "type C"

Each policy in DB2_POLICY has a DB2_POLICYTYPE discriminator that determines which detail table is joined. LGIPDB01 branches internally based on this value to populate the correct set of COMMAREA fields for the caller.

3.3 LGSTSQ — Transient Data Queue Logging Utility

3.3.1 Role and Purpose

LGSTSQ is a shared diagnostic utility program that writes structured error messages and raw data snapshots to a CICS Transient Data Queue (TDQ). It is invoked via EXEC CICS LINK by LGIPOL01 (and potentially other programs) whenever an error condition requires logging. It provides a centralized, consistent logging mechanism across the application.

3.3.2 Business Functions Performed

# Business Function Description
1 Structured Error Record Writing Writes a formatted ERROR_MSG record (date, time, program, customer/policy numbers, SQLCODE) to the TDQ
2 Raw COMMAREA Snapshot Logging Writes the first 90 bytes of the raw COMMAREA prefixed with 'COMMAREA=' as a secondary diagnostic record

3.3.3 Invocation Context from LGIPOL01

LGSTSQ is called up to twice per error event within LGIPOL01’s WRITE_ERROR_MESSAGE internal procedure:

  1. First call — logs the structured ERROR_MSG buffer (timestamp, program name, customer/policy numbers, SQLCODE).
  2. Second call — logs CA_ERROR_MSG containing the raw COMMAREA bytes (up to 90 bytes), provided EIBCALEN > 0.

4. End-to-End Data Flow

The following diagram illustrates the complete end-to-end data flow for a successful policy inquiry transaction, from the external caller through to the populated response:

sequenceDiagram participant Caller as External Caller participant POL as LGIPOL01 participant DB as LGIPDB01 participant DB2 as DB2 Database participant LOG as LGSTSQ / TDQ Caller->>POL: EXEC CICS LINK (COMMAREA: CA_CUSTOMER_NUM, CA_POLICY_NUM) POL->>POL: Capture EIBTRNID, EIBTRMID, EIBTASKN alt EIBCALEN = 0 POL->>LOG: EXEC CICS LINK LGSTSQ (ERROR_MSG: NO COMMAREA RECEIVED) POL->>Caller: EXEC CICS ABEND ABCODE(LGCA) else EIBCALEN > 0 POL->>POL: Set CA_RETURN_CODE = '00' POL->>POL: Copy CA_CUSTOMER_NUM, CA_POLICY_NUM → EM_CUSNUM, EM_POLNUM POL->>DB: EXEC CICS LINK LGIPDB01 (COMMAREA, Length=32000) DB->>DB2: SELECT from DB2_CUSTOMER, DB2_POLICY, [detail table] DB2-->>DB: Customer + Policy record DB-->>POL: Populated COMMAREA (all policy fields, CA_RETURN_CODE) alt CA_M_MAKE = 'HONDA' POL->>POL: Override CA_EXPIRY_DATE = '2099-01-01' end POL-->>Caller: EXEC CICS RETURN (Populated COMMAREA) end

This sequence captures the two key branching points: the COMMAREA presence check at entry, and the Honda expiry date override rule applied after data retrieval.

5. Business Rules Summary

All business rules in the application are currently implemented within LGIPOL01. They are organized by function:

5.1 Policy Inquiry and Data Retrieval

5.1.1 Customer Policy Record Retrieval

  • Purpose: Coordinate retrieval of comprehensive policy details for a specified customer and policy number.
  • Steps:
    1. Set CA_RETURN_CODE = '00' to establish a default success state.
    2. Pass CA_CUSTOMER_NUM and CA_POLICY_NUM in the COMMAREA and invoke LGIPDB01 via EXEC CICS LINK.
  • Significance: Failure to correctly pass parameters to the retrieval service prevents customer service representatives or downstream systems from viewing current policy contracts.

5.2 Motor Policy Term Adjustments

5.2.1 Honda Vehicle Policy Expiry Date Override

  • Purpose: Grant an indefinite coverage period for motor policies insuring Honda vehicles by overriding the stored expiry date.
  • Trigger Condition: CA_M_MAKE = 'HONDA' (case-sensitive, evaluated post-retrieval)
  • Action: CA_EXPIRY_DATE = '2099-01-01'
  • Significance: Incorrect application may cause premature policy expiration notices, accidental cancellation of active Honda coverage, or unauthorized lifetime coverage on non-qualifying vehicles — resulting in coverage disputes or financial liability.

6. Error Handling Strategy

The application uses a consistent two-phase error handling approach:

Phase Action Mechanism
Phase 1 — Log Capture timestamp, program name, customer/policy numbers, and raw COMMAREA WRITE_ERROR_MESSAGE → LGSTSQ → TDQ
Phase 2 — Abort Terminate the transaction to prevent corrupt data propagation EXEC CICS ABEND ABCODE('LGCA') NODUMP

The NODUMP option on the ABEND suppresses storage dump generation, reducing operational overhead for a known, anticipated error condition (missing COMMAREA).
