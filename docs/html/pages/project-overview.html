GenApp PLI Insurance Application — Project Overview

Project Overview

GenApp is a CICS-based general insurance policy management application written in PL/I, designed to run on IBM z/OS mainframe systems. It provides a complete policy lifecycle management system covering four insurance policy types: Endowment, House, Motor, and Commercial. The application exposes all core operations — Add, Inquire, Delete, and Update — through a structured three-tier CICS program architecture, backed by both DB2 relational storage and VSAM file storage.

1. Overview

GenApp (General Application) PLI serves as the authoritative back-end for insurance policy management on IBM z/OS. Terminal operators interact with the system via a BMS map screen, where they can manage the full lifecycle of any supported policy type. All inter-program communication is standardised through a shared 32,500-byte COMM_AREA structure, ensuring consistent data exchange across all tiers of the application.

1.1 Supported Policy Types

Policy Type Description
Endowment Life endowment insurance policies
House Residential property insurance policies
Motor Motor vehicle insurance policies
Commercial Commercial property and business insurance policies

1.2 Supported Operations

Operation Trigger Description
Add PF key — Add Creates a new policy record across DB2 and VSAM
Inquire PF key — Inquire Retrieves an existing policy and associated claims
Delete PF key — Delete Removes a policy from both DB2 and VSAM
Update PF key — Update Modifies an existing policy record in DB2 and synchronises VSAM

1.3 Key Application Facts

  • Language: PL/I (z/OS)
  • Runtime: IBM CICS
  • Primary Storage: IBM DB2 (relational)
  • Secondary Storage: VSAM KSDS (KSDSPOLY)
  • CICS Transaction: SSP1
  • CICS Resource Group: GENASAP
  • Total PL/I Programs: 11 (plus 1 supporting utility)
  • Shared Communication Area: LGCMAREA — 32,500-byte COMM_AREA union

2. System Architecture

GenApp PLI is organised as a classic three-tier CICS program architecture. Each tier has a clearly defined responsibility, and all tiers communicate using EXEC CICS LINK calls passing a shared COMM_AREA.

Terminal / UI tier  →  Business logic tier  →  Data access tier
    LGTESTP1              LGxPOL01               LGxPDB01  (DB2)
                                                 LGxPVS01  (VSAM)

2.1 Tier Descriptions

Tier Programs Responsibility
UI / Terminal LGTESTP1 Presents BMS map screen, captures operator input (PF keys/ENTER), dispatches to business logic

2.2 Communication Architecture

All programs share a single standardised communication structure defined in LGCMAREA.inc. This 32,500-byte area is passed as the entry parameter on every EXEC CICS LINK call, carrying both request inputs and response outputs between tiers.

PLI 
/* LGCMAREA.inc — Universal COMM_AREA structure (32,500 bytes) */
DCL COMM_AREA_PTR POINTER;
DCL 1 COMM_AREA BASED(COMM_AREA_PTR),
      /* Request header fields — operation type, policy type, policy number */
      /* Policy-specific data union — Endowment / House / Motor / Commercial */
      /* Response fields — return codes, error messages */
    ...;

3.1 UI Layer — LGTESTP1

LGTESTP1 is the sole entry-point program for the application, invoked by the SSP1 CICS transaction. It presents the SSMAPP1 BMS map to the terminal operator and handles all screen interaction logic including PF key dispatch, HANDLE AID, HANDLE CONDITION, and SYNCPOINT ROLLBACK for error recovery.

PLI 
/* Dispatch logic in LGTESTP1 — PF key to operation mapping */
WHEN (EIBAID = DFHPF1)
    EXEC CICS LINK PROGRAM('LGAPOL01')
         COMMAREA(COMM_AREA) LENGTH(32500);
WHEN (EIBAID = DFHPF2)
    EXEC CICS LINK PROGRAM('LGIPOL01')
         COMMAREA(COMM_AREA) LENGTH(32500);
WHEN (EIBAID = DFHPF3)
    EXEC CICS LINK PROGRAM('LGDPOL01')
         COMMAREA(COMM_AREA) LENGTH(32500);
WHEN (EIBAID = DFHPF4)
    EXEC CICS LINK PROGRAM('LGUPOL01')
         COMMAREA(COMM_AREA) LENGTH(32500);

3.2 Business Logic Layer

The four business logic programs (LGAPOL01, LGIPOL01, LGDPOL01, LGUPOL01) each follow the same pattern:

  1. Receive COMM_AREA from the UI tier
  2. Validate the incoming request fields
  3. Delegate to the appropriate DB2 or VSAM data access program
  4. Handle errors — log to TSQ via LGSTSQ and propagate return codes

LGAPOL01 additionally supports an optional call to the ODM business rules engine LGAPBR01, which is activated by setting BUSINESS_RULES = 'Y' in the COMM_AREA (disabled by default).

3.3 DB2 Data Access Layer

The DB2 access programs execute all SQL DML directly against the DB2 tables. The most feature-rich is LGIPDB01, which uses DB2 cursors for row-by-row iteration and CICS channels/containers for passing large result sets back to the caller:

PLI 
/* LGIPDB01 — cursor-based policy inquiry with CICS container return */
EXEC SQL DECLARE POLICY_CURSOR CURSOR FOR
    SELECT POLICYNUMBER, CUSTOMERNUMBER, ISSUEDATE, EXPIRYDATE,
           LASTCHANGED, BROKERID, BROKERSREFERENCE, PAYMENT
    FROM POLICY
    WHERE CUSTOMERNUMBER = :WS-CUSTOMER-NUM
    FOR READ ONLY;

EXEC SQL OPEN POLICY_CURSOR;

/* ... fetch loop ... */

EXEC CICS PUT CONTAINER(WS-CONTAINER-NAME)
         FROM(POLICY-DATA)
         FLENGTH(WS-DATA-LENGTH)
         CHANNEL(WS-CHANNEL-NAME);

3.4 VSAM Data Access Layer

The VSAM access programs operate on the KSDSPOLY KSDS file as a secondary, synchronised copy of policy data. Each operation maps directly to a CICS file command:

Program Operation CICS Command
LGAPVS01 Add EXEC CICS WRITE FILE('KSDSPOLY')
LGDPVS01 Delete EXEC CICS DELETE FILE('KSDSPOLY')
LGUPVS01 Update EXEC CICS READ FILE('KSDSPOLY') UPDATE + EXEC CICS REWRITE FILE('KSDSPOLY')

4.1 DB2 Tables

GenApp PLI uses six DB2 tables to store policy and claims data. The POLICY table serves as the master record, with four type-specific detail tables branching from it.

5. Operation Data Flows

The following sequence diagrams illustrate the end-to-end data flows for each of the four core operations.

5.1 Add Policy Flow

When an operator submits a new policy, LGTESTP1 dispatches to LGAPOL01, which optionally validates against business rules, then writes to both DB2 (via LGAPDB01) and VSAM (via LGAPVS01).

sequenceDiagram participant Op as Terminal Operator participant UI as LGTESTP1 participant BL as LGAPOL01 participant BR as LGAPBR01 participant DB as LGAPDB01 participant VS as LGAPVS01 participant D2 as DB2 participant KS as VSAM KSDSPOLY Op->>UI: Enter policy details, press PF-Add UI->>BL: EXEC CICS LINK (COMM_AREA) BL->>BL: Validate COMM_AREA alt BUSINESS_RULES = Y BL->>BR: EXEC CICS LINK (ODM validation) BR-->>BL: Validation result end BL->>DB: EXEC CICS LINK (DB2 path) DB->>D2: INSERT INTO POLICY DB->>D2: INSERT INTO MOTOR/HOUSE/ENDOWMENT/COMMERCIAL DB->>D2: INSERT INTO CLAIM DB->>D2: SELECT policy number D2-->>DB: New policy number DB-->>BL: Return policy number in COMM_AREA BL->>VS: EXEC CICS LINK (VSAM path) VS->>KS: EXEC CICS WRITE FILE KS-->>VS: Write confirmation VS-->>BL: Return code BL-->>UI: Return COMM_AREA with policy number UI-->>Op: Display confirmation on SSMAPP1

5.2 Inquire Policy Flow

Policy inquiry uses a dynamic CICS link to LGIPDB01, which performs cursor-based DB2 reads and returns data via CICS channels and containers.

sequenceDiagram participant Op as Terminal Operator participant UI as LGTESTP1 participant BL as LGIPOL01 participant DB as LGIPDB01 participant D2 as DB2 Op->>UI: Enter policy number, press PF-Inquire UI->>BL: EXEC CICS LINK (COMM_AREA) BL->>BL: Validate COMM_AREA BL->>DB: EXEC CICS DYNAMIC_LINK DB->>D2: SELECT FROM POLICY (cursor) D2-->>DB: Policy master record DB->>D2: SELECT FROM MOTOR/HOUSE/ENDOWMENT/COMMERCIAL D2-->>DB: Policy type detail DB->>D2: FETCH FROM CLAIM (cursor) D2-->>DB: Claim records DB->>DB: PUT CONTAINER (channel data) DB-->>BL: Return via CICS channel/container BL-->>UI: Return COMM_AREA UI-->>Op: Display policy data on SSMAPP1

5.3 Delete Policy Flow

Delete operations cascade from DB2 to VSAM — LGDPDB01 deletes the DB2 master record, then calls LGDPVS01 to remove the matching VSAM record.

sequenceDiagram participant Op as Terminal Operator participant UI as LGTESTP1 participant BL as LGDPOL01 participant DB as LGDPDB01 participant VS as LGDPVS01 participant D2 as DB2 participant KS as VSAM KSDSPOLY Op->>UI: Enter policy number, press PF-Delete UI->>BL: EXEC CICS LINK (COMM_AREA) BL->>BL: Validate COMM_AREA BL->>DB: EXEC CICS DYNAMIC_LINK DB->>D2: DELETE FROM POLICY D2-->>DB: Delete confirmation DB->>VS: EXEC CICS LINK VS->>KS: EXEC CICS DELETE FILE KS-->>VS: Delete confirmation VS-->>DB: Return code DB-->>BL: Return code in COMM_AREA BL-->>UI: Return COMM_AREA UI-->>Op: Display confirmation on SSMAPP1

5.4 Update Policy Flow

Update operations use a SELECT FOR UPDATE cursor to lock the DB2 row before modifying it, then synchronise the VSAM copy via LGUPVS01.

6. Supporting Infrastructure

6.1 Error Logging — LGSTSQ

Every program in GenApp PLI uses LGSTSQ as a centralised error logging utility. When any operation fails — whether a DB2 error, a VSAM error, or a CICS condition — the program invokes LGSTSQ via EXEC CICS LINK to write a diagnostic message to a CICS transient data queue (TDQ). This ensures consistent and auditable error tracking across the entire application.

PLI 
/* Error handling pattern used across all GenApp PLI programs */
ON ERROR BEGIN;
    EXEC CICS LINK PROGRAM('LGSTSQ')
         COMMAREA(ERROR_MSG) LENGTH(LENGTH(ERROR_MSG));
    EXEC CICS SYNCPOINT ROLLBACK;
    EXEC CICS RETURN;
END;

6.2 Business Rules Engine — LGAPBR01

LGAPBR01 is an optional IBM Operational Decision Manager (ODM) business rules adapter called exclusively by LGAPOL01 during the Add Policy flow. It is disabled by default and is activated only when BUSINESS_RULES = 'Y' is set in the COMM_AREA. The business rules request/response structures are defined in LGCMARER.inc.

6.3 BMS Maps

The application uses one active BMS mapset:

Mapset Map File Used By Direction
SSMAP SSMAPP1 Maps/SSMAP.bms LGTESTP1 SEND MAP + RECEIVE MAP

The SSMAP.inc include also defines symbolic maps SSMAPP2–SSMAPP5 and SSMAPC1, though only SSMAPP1 is actively used by LGTESTP1 in the current implementation.
