GenApp PLI Insurance Application — Project Overview

Project Overview

GenApp is a CICS-based general insurance policy management application written in PL/I, designed to run on IBM z/OS mainframe systems. It provides a complete policy lifecycle management system covering four insurance policy types: Endowment, House, Motor, and Commercial. The application exposes all core operations — Add, Inquire, Delete, and Update — through a structured three-tier CICS program architecture, backed by both DB2 relational storage and VSAM file storage.

1. Overview

GenApp (General Application) PLI serves as the authoritative back-end for insurance policy management on IBM z/OS. Terminal operators interact with the system via a BMS map screen, where they can manage the full lifecycle of any supported policy type. All inter-program communication is standardised through a shared 32,500-byte COMM_AREA structure, ensuring consistent data exchange across all tiers of the application.

GenApp PL/I Insurance Application — Project Overview

1. Project Overview

The General Insurance Application (GenApp) is a modular, enterprise-grade mainframe insurance platform written in PL/I, deployed on IBM z/OS CICS Transaction Server. It provides end-to-end lifecycle management for insurance policies — including creation, inquiry, update, and deletion — persisting data across IBM Db2 for z/OS relational tables and VSAM KSDS datasets.

GenApp is structured as a multi-tier CICS application in which each tier has a clearly defined responsibility: a presentation layer handles terminal and web interactions, a business logic layer orchestrates policy operations and enforces rules, and a data access layer manages all persistence concerns. Cross-cutting concerns such as error logging and audit trailing are handled by shared utility programs and canonical copybooks used consistently across all modules.

The architecture enforces a strict top-down call hierarchy: external callers interact only with the presentation or business layers, business logic programs invoke only DAL programs, and DAL programs interact directly with DB2 and VSAM. No layer bypasses another, ensuring separation of concerns and maintainability.

3. Application Layers and Components

The presentation layer is represented by a single BMS 3270 terminal driver program, LGTESTP1, which acts as both a user interface controller and a test harness. It accepts input from 3270 screens rendered via BMS mapset SSMAPP1, translates screen fields (customer number, policy type, policy-specific data) into the canonical COMMAREA payload, and dispatches to the appropriate business logic module based on the user’s function key selection:

3.2.1 Policy Inquiry — LGIPOL01

LGIPOL01 is the most illustrative example of the business logic tier’s pattern. It validates that a COMMAREA was received, delegates the DB2 retrieval to LGIPDB01, and applies a post-retrieval business rule specific to motor policies.

A notable hard-coded business rule exists: if the retrieved motor policy’s vehicle make is HONDA, the policy expiry date is unconditionally overridden to 2099-01-01.

3.2 Business Logic Layer

The four business logic programs (LGAPOL01, LGIPOL01, LGDPOL01, LGUPOL01) each follow the same pattern:

  1. Receive COMM_AREA from the UI tier
  2. Validate the incoming request fields
  3. Delegate to the appropriate DB2 or VSAM data access program
  4. Handle errors — log to TSQ via LGSTSQ and propagate return codes

LGAPOL01 additionally supports an optional call to the ODM business rules engine LGAPBR01, which is activated by setting BUSINESS_RULES = 'Y' in the COMM_AREA (disabled by default).

3.3 DB2 Data Access Layer

The DB2 access programs execute all SQL DML directly against the DB2 tables. The most feature-rich is LGIPDB01, which uses DB2 cursors for row-by-row iteration and CICS channels/containers for passing large result sets back to the caller:

PLI 
/* LGIPDB01 — cursor-based policy inquiry with CICS container return */
EXEC SQL DECLARE POLICY_CURSOR CURSOR FOR
    SELECT POLICYNUMBER, CUSTOMERNUMBER, ISSUEDATE, EXPIRYDATE,
           LASTCHANGED, BROKERID, BROKERSREFERENCE, PAYMENT
    FROM POLICY
    WHERE CUSTOMERNUMBER = :WS-CUSTOMER-NUM
    FOR READ ONLY;

EXEC SQL OPEN POLICY_CURSOR;

/* ... fetch loop ... */

EXEC CICS PUT CONTAINER(WS-CONTAINER-NAME)
         FROM(POLICY-DATA)
         FLENGTH(WS-DATA-LENGTH)
         CHANNEL(WS-CHANNEL-NAME);

3.4 Cross-Cutting Services

3.4.1 Error and Audit Logging — LGSTSQ

LGSTSQ is a shared CICS utility program invoked via EXEC CICS LINK from any program across all layers whenever an error is detected. It writes timestamped diagnostic records — including program name, customer number, policy number, SQLCODE, and up to 90 bytes of raw COMMAREA content — to a CICS Transient Data Queue (TDQ).

PLI 
/* Log primary error message */
EXEC CICS LINK PROGRAM('LGSTSQ')
    COMMAREA(ERROR_MSG)
    LENGTH(LENGTH(ERROR_MSG));

/* Log raw COMMAREA dump (up to 90 bytes) */
IF EIBCALEN < 91 THEN
    CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
ELSE
    CA_DATA = LEFT(COMM_AREA_RAW, 90);

EXEC CICS LINK PROGRAM('LGSTSQ')
    COMMAREA(CA_ERROR_MSG)
    LENGTH(LENGTH(CA_ERROR_MSG));

5.3 Delete Policy Flow

Delete operations cascade from DB2 to VSAM — LGDPDB01 deletes the DB2 master record, then calls LGDPVS01 to remove the matching VSAM record.

5.4 Update Policy Flow

Update operations use a SELECT FOR UPDATE cursor to lock the DB2 row before modifying it, then synchronise the VSAM copy via LGUPVS01.

6. Supporting Infrastructure

6.1 Error Logging — LGSTSQ

Every program in GenApp PLI uses LGSTSQ as a centralised error logging utility. When any operation fails — whether a DB2 error, a VSAM error, or a CICS condition — the program invokes LGSTSQ via EXEC CICS LINK to write a diagnostic message to a CICS transient data queue (TDQ). This ensures consistent and auditable error tracking across the entire application.

5. Policy Types Supported

5.1 Endowment Policies

Endowment policies are life insurance contracts that guarantee a payout (CA_E_SUM_ASSURED) at maturity or upon death. When adding an endowment policy, the business rules engine LGAPBR01 is invoked to validate policy terms, limits, and applicable rates before insertion.

5.2 House Policies

House policies cover residential property. Policy data is stored in the HOUSE DB2 table and carries standard policy header attributes (issue date, expiry date, payment amount) alongside property-specific fields.

5.3 Motor Policies

Motor policies insure vehicles. The MOTOR DB2 table stores vehicle details including make (CA_M_MAKE) and model. A notable application-level business rule applies to motor policies: any policy where the vehicle make is HONDA has its expiry date unconditionally overridden to 2099-01-01 by the inquiry orchestrator LGIPOL01.

6.2 Business Rules Engine — LGAPBR01

LGAPBR01 is an optional IBM Operational Decision Manager (ODM) business rules adapter called exclusively by LGAPOL01 during the Add Policy flow. It is disabled by default and is activated only when BUSINESS_RULES = 'Y' is set in the COMM_AREA. The business rules request/response structures are defined in LGCMARER.inc.

5.4 Commercial Policies

Commercial policies insure business premises. The CA_B_PROPTYPE field (255 characters) holds the commercial property classification, stored in the COMMERCIAL DB2 table.

6. Error Handling and Operational Behaviour

6.1 COMMAREA Validation

Every business logic program validates the presence of a COMMAREA immediately on entry by inspecting EIBCALEN. If no COMMAREA is supplied (EIBCALEN = 0), the program:

  1. Formats a timestamped error message.
  2. Writes it to the diagnostic TDQ via LGSTSQ.
  3. Abends the transaction with a named abend code (e.g., LGCA) using NODUMP.
PLI 
/* LGIPOL01 — COMMAREA presence check */
IF EIBCALEN = 0 THEN DO;
    EM_MSG_TEXT = ' NO COMMAREA RECEIVED';
    CALL WRITE_ERROR_MESSAGE;
    EXEC CICS ABEND ABCODE('LGCA') NODUMP;
END;

6.3 Diagnostic Logging Pattern

All programs across all layers follow a consistent diagnostic logging pattern via LGSTSQ. Each log record carries:

  • Formatted date and time (obtained via EXEC CICS ASKTIME / EXEC CICS FORMATTIME)
  • Program name
  • Customer number and policy number
  • SQLCODE or error descriptor
  • Up to 90 bytes of raw COMMAREA content (where available)
